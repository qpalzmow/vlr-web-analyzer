# VLR Web Analyzer

FastAPI, SQLite 및 일반 JavaScript로 구성된 VLR 경기 분석기입니다.

## 실행

```powershell
python -m pip install -r requirements.txt
python server.py
```

기본 포트는 7860이며 PORT 환경변수로 변경할 수 있습니다. Docker는 `python -m app.entrypoint`로 같은 환경변수를 읽습니다.

## 경기 중심 화면

- 대회와 경기를 고르면 저장된 경기 정보로 매치업 Hero를 즉시 표시합니다. Hero의 분석 버튼으로 기존 `/api/analyze`를 한 번 호출해 전체 기록을 표시합니다.
- Overview 모듈은 예정 경기에서 맵 비교, 라이브에서 현재 스코어, 종료 후 확정 결과와 실제 밴픽을 먼저 표시합니다. Maps, Players, Form 상세 표와 공유·이미지 저장은 유지됩니다.
- `public/design/`은 색상·간격·타이포그래피·배치·모션을, `public/components/`는 Hero·요약·맵·커리어 표현을 담당합니다. `public/pages/match.js`가 기존 렌더링과 연결하며 API 응답과 분석 계산은 바꾸지 않습니다.
- 맵 승률은 과거 기록, ACS는 전체 커리어 지표입니다. 실제 스코어와 구분하며 표본이 5맵 미만인 맵은 우위 설명에서 제외합니다. 모션 감소 설정을 지원합니다.

## 1시간마다 준비하는 경기 목록

- 경기 선택 → 대회 필터 선택 → 전력 분석 버튼 순으로 사용합니다. 공유 링크는 저장된 필터로 자동 분석합니다.
- 수집기가 경기 일정, 확정된 팀 ID, 양 팀의 대회 목록, 맵 풀을 1시간 갱신 목표로 준비합니다. Render에서는 GitHub Actions가 수집하며 웹 서버가 잠들어 있어도 저장은 계속됩니다. 팀과 대회별 중복 요청은 한 번으로 합칩니다.
- 수집이 끝나면 전체 목록을 SQLite에 한 번에 교체합니다. 갱신 중에는 이전 목록을 계속 제공하고, 실패했다고 목록을 비우거나 클릭 시 외부 사이트를 조회하지 않습니다.
- 화면은 `/api/catalog`에서 완성된 목록을 받아 저장합니다. 경기 선택은 브라우저 안에서 즉시 처리하며 상세 정보·대회 목록·맵 풀·점수를 요청하지 않습니다. 기존 상세 API도 저장된 목록만 읽습니다.
- 화면은 1분마다 새로 게시된 목록이 있는지만 확인합니다. 진행 중인 분석과 선택한 필터는 유지됩니다. 상단에 실제 데이터 기준 시각을 표시하며 예약 수집이 늦어져도 새 데이터처럼 표시하지 않습니다.
- 대진이 확정되지 않은 경기는 `대진 미정`, 수집되지 않은 경기는 `업데이트 대기`로 표시합니다. 이전에 준비된 동일 대진은 수집 실패 시 이전 데이터를 사용합니다.
- `data/catalog_seed.json`은 실제 수집한 공개 경기 데이터입니다. 처음 배포할 때 초기 목록으로 사용하며, 기존 SQLite 데이터가 있으면 그것을 우선 사용합니다. 이후 목록은 서버가 자동 갱신합니다.

## 한 번에 표시하는 전력 분석

- 수집기가 경기 목록에 있는 팀의 맵 전적과 현역 선수의 커리어 정보를 미리 준비합니다. `/api/analyze`와 이전 버전의 개별 분석 API 모두 저장된 데이터만 읽습니다.
- 대회를 선택하면 승패·공수 라운드 합계를 합산해 맵 승률을 계산합니다. 불참 대회에 전체 기간의 데이터를 대신 표시하지 않습니다. 최근 흐름은 필터와 별개로 최근 완료 경기 5개입니다.
- 선수 표는 기록이 있는 현역 등록 선수 중 커리어 ACS가 가장 높은 선수를 팀별로 비교합니다. 코치·스태프·비활성·서브 표식을 가진 선수는 제외합니다. 일부 선수의 기록이 비면 표본과 누락 선수를 안내하며, 실제 기록이 있는 선수의 수치는 유지합니다. 현역 명단을 검증하지 못했거나 기록이 전혀 없으면 비교 불가를 표시합니다.
- 선수 커리어는 팀 맵 기록의 대회 필터와 별개로 전체 커리어를 비교합니다. 현재 소속만으로 과거 대회의 소속과 참여 경기 전체를 검증할 수 없으므로 대회별 선수 지표로 표현하지 않습니다. 팀 경기 집합과 일치하는 FK/FD 표본이 없으므로 팀 FK/FD와 기존 예측 승률은 `null`입니다. 커리어 합계를 팀 라운드로 나누지 않습니다.
- 맵 밴·픽은 전적 기반의 참고 추천입니다. BO 형식과 대회 veto 규칙을 확인하지 않은 상태에서 결정 맵을 만들지 않습니다. 나머지 맵 후보도 표시합니다.
- 범위별 수집 실패는 이전 값을 유지합니다. 팀 단위 `last_attempt_at`, `last_success_at`, `last_error`를 기록하며, 1시간 이상 된 범위는 `stale`로 안내합니다. `/api/catalog`의 `analytics_status`와 `/api/sync/status`의 `analytics`는 경기 목록 수집 상태와 별개입니다.
- `data/analysis_seed.json`은 공개 데이터를 수집한 초기 분석값입니다. 이미 저장된 데이터는 보존하며, 오래된 초기값도 freshness 검사에서 예외 처리하지 않습니다. 초기값이 없는 팀·대회는 즉시 409로 준비 중임을 알립니다.
- 점수는 분석 뒤 독립적으로 갱신합니다. 목록에 등록된 경기만 조회하고, 슬러그·쿼리가 달라도 경기 ID 하나로 캐시합니다. LIVE 25초, UPCOMING 60초 간격이며 실제 상태 전용 요소가 FINAL일 때 중지합니다.

## 자동 동기화 및 수동 관리

로컬 실행에서는 `app/catalog.py`의 전용 작업이 수집 시작 시각 기준 1시간 간격으로 갱신합니다. 팀 통계 예열은 별도 작업이라 경기 목록 갱신을 막지 않습니다. 작업 중 도착한 최신 목록을 보관해 현재 작업 종료 후 이어서 처리합니다. SQLite의 5분 임대 잠금을 1분마다 갱신해 중복 수집을 막으며, 중단된 작업은 임대 만료 후 복구합니다. 전체 수집 실패 시 이전 목록을 유지하고 5분 뒤 재시도합니다.

Render 무료 플랜의 서버는 절전·재시작될 수 있으므로 수집과 보관을 맡지 않습니다. `.github/workflows/hourly-data.yml`이 외부에서 수집하고, 경기 목록과 완료된 팀 분석을 `catalog-data` 브랜치의 단일 `snapshot.json`에 영구 보관합니다. Render의 SQLite는 언제든 다시 만들 수 있는 조회용 캐시입니다. 서버가 꺼져 있거나 로컬 파일이 사라져도 다음 시작에서 공개 게시본으로 복구합니다. 수집기는 Render를 깨우는 HTTP 요청을 보내지 않으며, 웹 서버의 응답 여부와 데이터 게시 성공을 분리합니다.

GitHub Actions는 매시간 7·22·37·52분(UTC, 한국 시각도 동일한 분)에 게시된 경기 목록이 1시간 이상 오래됐는지 확인합니다. 아직 1시간이 지나지 않았다면 수집을 생략합니다. 예약 실행의 지연·누락과 수집 소요 시간 때문에 정확한 매시간 갱신을 보장하지 않습니다. 데이터 기준 시각과 갱신 지연 상태를 보고 실제 최신성을 판단해야 합니다. 수집 코드·설정·워크플로를 `master`에 수정하면 즉시 수집을 시작하며, `workflow_dispatch`로 전체 수집 또는 경기 목록만 수동 갱신할 수도 있습니다. `check_source` 입력은 게시 없이 기존 소스 시각 파싱 검사만 실행합니다.

게시 브랜치는 애플리케이션 코드 브랜치와 분리되어 수집마다 사이트를 재배포하거나 자동 푸시와 충돌하지 않습니다. GitHub의 저장소 전용 `GITHUB_TOKEN`을 쓰며 추가 비밀키 설정은 필요하지 않습니다. 각 실행은 이전 게시본을 먼저 복원합니다. Actions 캐시가 남아 있다면 `.collector-data`의 파싱 결과도 재사용해 중복 조회를 줄이지만, 캐시는 삭제되거나 복원에 실패할 수 있으므로 데이터 보관 수단으로 의존하지 않습니다. 영구 원본은 계속 `catalog-data`입니다.

Render의 기본 환경변수 `RENDER=true`를 감지하면 서버는 직접 수집하는 대신 공개 스냅샷을 사용합니다. 시작 시 최신 스냅샷을 가져온 다음, 실행 중에는 5분마다 새 게시본을 확인합니다. 첫 화면도 가져온 목록으로 시작합니다. 경기 목록과 분석 데이터는 하나의 SQLite 트랜잭션으로 설치하며, 더 새로운 로컬 데이터를 오래된 게시본으로 덮어쓰지 않습니다. 실제 수집 시각과 범위별 실패 정보는 보존합니다. 게시본 오류 시 이전 데이터로 서비스를 계속하고 5분 뒤 재시도합니다. 경기 목록이 2시간 이상 오래되면 화면에 `갱신 지연`을 표시합니다.

외부 수집은 경기 목록에 10분 작업 예산을 적용하고 새 목록을 먼저 게시한 뒤 분석을 별도로 준비합니다. 목록 예산이 끝나면 준비된 대진을 보존하고, 갱신하지 못한 동일 대진은 이전 기록을 유지합니다. 분석은 40분 작업 예산과 45분 실행 제한을 사용하며, 시간 제한에 도달하면 마지막 유효 체크포인트까지 완료된 분석을 게시합니다. 수집 중 체크포인트는 최대 1분마다 원자적으로 저장하고, 정상 종료 시 모든 결과를 최종 저장합니다. 최신 범위는 재사용하고 누락·실패·오래된 기록부터 갱신하며, 외부 요청 사이에 최소 1초 간격을 둡니다. 최근 목록에 포함된 팀을 기준으로 준비 상태를 집계하고, 이전 팀과 대회 기록도 유지합니다. 일부 범위가 실패해도 그 범위의 이전 통계를 지우지 않습니다. 일부 완료·시간 초과는 Actions 요약과 경고, 게시본의 `collection` 상태에 기록하며, 성공한 경기 목록과 모든 선수 분석의 갱신 성공을 같은 것으로 취급하지 않습니다.

로컬 실행은 기존 서버 내부 1시간 수집을 유지합니다. `VLR_REFRESH_MODE=snapshot` 또는 `local`로 방식을 명시할 수 있습니다. 영구 디스크를 사용한다면 `VLR_DATA_DIR`을 그 디스크 경로로 지정하세요. 외부 스냅샷은 공개 통계만 포함하며 소스 캐시, 관리 토큰, DB 파일은 게시하지 않습니다.

`POST /api/sync/trigger` 및 `POST /api/cache/warm`은 기본적으로 비활성화(503)되어 있습니다. 수동 실행이 필요하면 서버의 VLR_MAINTENANCE_TOKEN 환경변수에 별도의 비밀값을 설정하고, 요청의 Authorization 헤더에 `Bearer <설정한 값>`을 전달합니다. 토큰을 화면 JavaScript에 넣지 마세요. 인증 실패는 401, 이미 실행 중이면 409, 직전 수동 실행 시작 후 5분이 지나지 않았으면 429를 반환합니다. 이 설정은 자동 동기화에 영향을 주지 않습니다.

## 테스트

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
node --test tests/frontend.test.cjs
```

GitHub Actions에서 Python 3.11 및 Node 22 테스트를 실행합니다. `tests/fixtures`는 2026-09-22 실제 VLR 페이지에서 확보한 공개 HTML 조각입니다. Python 테스트는 임시 SQLite DB와 대체 수집 함수를 사용합니다. 프런트엔드 테스트는 Node의 내장 테스트 도구와 DOM 대체 객체로 경기 선택, 필터, 공유 링크, 점수 갱신, 차트를 검증합니다. 실제 VLR 연동, 실제 브라우저, Docker 실행 검증과는 구분됩니다.

## 코드 및 실행 파일 정리

현재 수집 경로는 `app/catalog.py`, `app/analysis.py`, `app/snapshot_export.py`입니다. 사용하지 않던 이전 동기화·캐시 예열·스크레이퍼 경로와 일회성 진단 스크립트는 제거했습니다. 이전 버전의 API 주소와 요청 형식은 유지합니다. 기존 SQLite의 이전 테이블과 실제 수집 데이터도 삭제하지 않습니다.

목록 상태는 선수·맵 전체 데이터 대신 메타데이터만 조회합니다. 초기 분석 seed는 단일 트랜잭션으로 누락 팀만 삽입합니다. Docker에는 실행 코드, 프런트엔드, 공개 seed만 포함하며 로컬 DB, 데스크톱 빌드 결과, 테스트와 자동 푸시 스크립트를 포함하지 않습니다.

## 자동 푸시 스크립트

auto_push.ps1은 60초마다 변경을 커밋하고 origin/master로 푸시합니다. 사용자 요청에 따라 자동 푸시를 유지합니다. 큰 변경은 별도 작업 디렉터리에서 검증한 뒤 원본 프로젝트에 반영합니다.
